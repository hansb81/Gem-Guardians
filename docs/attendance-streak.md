## 2. 적절한가? — 다이아 양은 OK, 아이템은 약함

### 2-1. 다이아 (주 95 = 하루 13.6)

| 비교 | 하루 다이아 | 출석 대비 |
|---|---|---|
| 출석(지금) | 13.6 | 1.0 |
| 주간 패스 5,900원 (100 + 60×7 = 520 / 7일) | 74 | 출석의 5.5배 |
| 월간 패스 11,000원 (300 + 100×30 = 3,300 / 30일) | 110 | 출석의 8배 |

- 출석은 패스의 **12~18%**. 보통 "무료 일일 = 패스 일일의 10~25%" 범위라 **패스를 깎아 먹지 않습니다.** 패스는 출석 위에 더해지는 것이라 경쟁 관계도 아님.
- 한 달 무과금 다이아 ≈ 410개 = dia.1(5,900원, 330개) 조금 넘는 양. 4번째 슬롯(100) + 깃털 몇 개 + 골드 교환 몇 번 정도 → "꾸준히 오면 조금씩 쌓이는" 적당한 수준.
- 골드 교환 small(20다이아 = 일반 층 1개 보상) 기준으로 주 95다이아 ≈ 일반 층 4~5개 분량 골드. 광산 골드(하루 상한) 보다 작아 메인 골드 밸런스(v12-10/v13)에 영향 거의 없음.

## 3. 7일 연속 보너스 설계

### 3-1. 규칙 (추천안 = "누적판 + 연속 줄" 두 갈래)

- **출석판(7칸)은 지금처럼 누적**: 빠져도 안 끊김, 다음 칸부터. (캐주얼 친화 유지, 기존 결정 S-2 그대로)
- **연속 출석은 따로 셈**: KST 날짜로 **어제도 받았으면 +1, 하루라도 비면 오늘이 1일**로 다시 시작.
- **연속 7일째마다 보너스**(7, 14, 21 … 계속 반복). 출석판 몇째 칸이든 상관없음.
- 빠진 날을 메우는 "보충"·"보호권"은 v1에 없음(나중에 이벤트로 검토).
- 기준 시각 00:00 KST(랭킹 시즌과 같음). 기기 시계는 표시용만.

왜 이 방식인가:
- "출석판 7칸을 연속으로 채워야 보너스"로 묶으면 2일째에 한 번 빠진 사람은 남은 5일 동안 보너스 기회가 없어 동기가 꺾임.
- "끊기면 출석판도 1일로"는 지금의 끊김 없는 규칙을 깨고 7일째 큰 보상을 잃는 벌칙이 너무 셈.
- 연속 줄을 따로 두면 끊겨도 바로 다음 날부터 다시 7일을 노릴 수 있음. 출석판을 하루도 안 빠지고 채우면 7일째에 판 보상 + 연속 보너스가 겹쳐 크게 터짐.

### 3-2. 연속 보너스 보상 (추천)

**다이아 30 + 불사조 깃털 1** (깃털 = 다이아 50 상당)

| 무과금, 하루도 안 빠짐 | 주 다이아 | 하루 | 주간 패스 대비 |
|---|---|---|---|
| 지금 | 95 | 13.6 | 18% |
| 추천(판 + 연속) | 125 | 17.9 | 24% (월간 패스의 16%) |

- 아이템까지 다이아로 환산하면 주 ≈ 220다이아 상당이지만, 패스는 이것 **위에** 더해지는 상품이라 여전히 패스 구매 이유가 남음.
- 깃털은 광고 이어하기(하루 5회)와 같은 효과라 희소성을 크게 해치지 않음. 광고가 없는 웹·토스 사용자에겐 특히 반가운 보상.
- 다른 안: 다이아 50만(깔끔, 주 145) / 다이아 20 + 황금 주화 1(골드 ×2라 골드 밸런스에 조금 영향). 추천은 깃털안.
- 값은 `config/attendance.json`의 `streak` 한 곳 + 서버 사본에서만 바꿈(테스트가 같은지 확인).

### 3-3. 서버 (Supabase)

새 마이그레이션 `server/supabase/migrations/20261121000000_att_streak.sql` (S1 파일은 고치지 않음)

```sql
alter table public.attendance
  add column streak int not null default 0,      -- 지금 연속 일수
  add column best_streak int not null default 0, -- 최고 기록(운영 참고)
  add column streak_bonuses int not null default 0; -- 연속 보너스 받은 횟수
```

- **기존 플레이어 되채우기**: `claims`의 `att:YYYY-MM-DD` 날짜로 "last_date에서 끝나는 연속 구간 길이"를 계산해 `streak`, `best_streak`에 넣음(gaps-and-islands 한 번). 단, `last_date`가 오늘(배포일 KST)·어제가 아니면 0.
- **`att_claim` 교체**: 인자 `p_streak jsonb`(= `{ goal:7, bonus:{...} }`) 추가. 옛 3인자 함수는 drop 후 4인자로 create(Edge Function과 한 번에 배포).
  - 같은 트랜잭션, 같은 `for update` 잠금 안에서:
    - `last_date = p_today - 1` → `streak + 1`, 그 외(처음·빠짐) → `1`
    - `streak % goal = 0` 이면 보너스 → `bundle = 판 보상 + 연속 보너스` 합침(다이아 더하기, 아이템 개수 더하기). `streak_bonuses + 1`.
    - `best_streak = greatest(best_streak, streak)`
  - **txId는 그대로 `att:{날짜}` 1개**, 합친 bundle 1개 → 기기 `grantClaim`·`claims-pending` 복구 경로를 하나도 안 바꿔도 됨. 같은 날 두 번 = 기존처럼 `already`.
  - 응답에 추가: `streak`, `streakBonus`(받았으면 보너스 bundle, 아니면 null). 팝업 표시용.
  - 합치기는 SQL 함수 `public.bundle_add(a jsonb, b jsonb)`(service_role만 실행). bundle 모양 = `{ diamonds?, gold?, items?{id:n} }` 기준.
- **`att-status` / `hello`의 att**: `streak`(표시용: `last_date`가 오늘·어제가 아니면 0 = 끊김), `streakBroken`(어제 안 받아 끊긴 상태인지), `streakGoal`, `streakBonus`(보상표) 추가.
- 서버 사본 `_shared/attendance.ts`에 `ATTENDANCE_STREAK` 추가.
- 계정 연결·병합(account-merge): attendance 행은 **남는 계정 쪽 기록 유지**(게스트 쪽 연속은 합치지 않음). 문서에 한 줄.

### 3-4. 기기 (게임)

- `config/attendance.json`: `"streak": { "goal": 7, "bonus": { "diamonds": 30, "items": { "revive": 1 } } }`, 2·4·6일 아이템 교체.
- `AttendanceService.claim()`: 응답 `streak`, `streakBonus`를 `status`에 반영. 지급은 그대로 `grantClaim` 1번.
- 획득 팝업: 보너스가 있으면 제목 "7일 연속 출석 보너스!" + 합친 보상 표시(공통 획득 팝업에 제목만 넘김).
- **하루 첫 메뉴 진입 때 출석 팝업 자동으로 1회 열기**(오늘 안 받았고 튜토리얼 끝났을 때, 하루 1번만 기기 기록). 연속이 "버튼을 안 눌러서" 끊기는 일을 줄임. 팝업 안 "받기"는 그대로 직접 누름.
